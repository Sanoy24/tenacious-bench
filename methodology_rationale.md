# Path B Methodology Rationale

## Path Selection

**Path B — Preference-tuned judge/critic** was chosen over Path A (SFT rewrite) and Path C (stepwise critic).

The Week 10 evidence points to an **inconsistency problem**: the system sometimes follows policy and sometimes does not on nearly identical inputs. Probes P007, P011, P027, and P032 all triggered at 100% across three simulation runs. Three concrete zero-reward traces confirm the pattern:

- `879ee1fc-7a7f-438e-bb19-054fb43c8637` — signal over-claiming on LOW-confidence hiring data (P007)
- `88bb3cea-1599-471c-9609-27736556d1e0` — bench over-commitment against zero available engineers (P011)
- `09f0188f-8567-4e62-b62c-08cc164774e5` — timezone fabrication with no prospect timezone provided (P027)

All three are zero-reward traces. The agent did not produce a wrong output by accident — it consistently failed to recognize when available evidence did not meet the threshold for a strong claim. A preference-tuned judge/critic is the direct response: train a model to discriminate between evidence-calibrated and over-claiming outreach on these exact failure modes.

Path A (SFT) would teach the model to generate better outreach but would not give it a signal about *why* a specific output violates policy. Path C (stepwise critic) requires trajectory data we do not have from Week 10. Path B uses the existing benchmark tasks directly as preference pairs.

## Algorithm Selection: SimPO

**SimPO** (Meng, Xia, and Chen, NeurIPS 2024) was chosen over DPO (Rafailov et al., NeurIPS 2023) and ORPO (Hong et al., 2024).

SimPO eliminates the frozen reference model by optimizing the direct log-probability margin `log π(y_w|x) − log π(y_l|x) > γ`. This halves the VRAM requirement vs. DPO (one forward pass per batch instead of two), which is the binding constraint on Colab T4 with a Qwen 2.5 3B backbone and LoRA. (Qwen3.5-4B was the original plan but its GatedDeltaNet hybrid architecture requires bfloat16, which T4 does not support natively; Qwen2.5-3B-Instruct is a standard transformer that runs in fp16 on T4.)

**Why not DPO**: DPO's reference model provides a distribution drift bound but requires two forward passes per training step. At Qwen 2.5 3B + LoRA on 16 GB VRAM, this forces batch size = 1, which destabilizes training on a 600–1,200 pair dataset. The reference model's role (preventing drift from SFT baseline) is replicated here by a dev-set evaluator-agreement monitor running every 100 training steps.

**Why not ORPO**: ORPO merges SFT and preference objectives, which requires clean SFT data alongside the preference pairs. Tenacious-Bench Path B has only preference pairs; running ORPO without separate SFT examples risks the model updating base language modeling toward the narrow outreach domain rather than learning the preference direction.

**SimPO hyperparameters**: β = 2.0, γ = 1.0 (γ/β = 0.5) for the headline run; γ = 1.5 (γ/β = 0.75) as the upper-edge ablation. The γ/β ≈ 0.5 region is the best-performing configuration in the SimPO paper's Table 3 (Meng et al. 2024) for both Mistral-Base (β=2.0, γ=0.5 → γ/β=0.25) and Llama-3-8B-Instruct (β=2.5, γ=1.4 → γ/β=0.56); γ/β > 1.0 is reported as unstable on small preference sets. Both results reported in `ablations/ablation_results.json`. Fixed seed 42. LoRA rank 16, alpha 32.

**Known weakness**: SimPO's reference-free assumption is weaker for narrow-domain training where chosen and rejected outputs have similar base log-probabilities. Mitigation: evaluate `scoring_evaluator.py` agreement on the dev partition every 100 steps and roll back to the previous checkpoint if agreement drops below the SFT baseline.

## Data Preparation Recipe

**Source**: `tenacious_bench_v0.1/train/` (121 tasks) and `tenacious_bench_v0.1/dev/` (73 tasks). Held-out partition (48 tasks) never touched.

**Rejected side**: the existing `candidate_output` from each task — intentionally flawed outputs authored at benchmark construction time. Each must fail at least one check under `scoring_evaluator.py` (`passed_all_checks: false`). Tasks where the rejected output unexpectedly passes are dropped.

**Chosen side**: corrected rewrites generated by **DeepSeek V3.2** (`deepseek/deepseek-chat-v3-0324`) via OpenRouter. Each rewrite must pass all checks under `scoring_evaluator.py` (`passed_all_checks: true`). Rewrites that fail the evaluator are dropped; up to 3 retries per task.

**Preference-leakage prevention** (Li et al., 2025): the judge backbone is Qwen 2.5 3B Instruct. The chosen-rewrite generator is DeepSeek V3.2 — a non-Qwen-family model. This family rotation prevents the judge from learning to prefer Qwen-style phrasings over evidence-calibrated content. The primary quality control is evaluator-pass validation (family-independent, deterministic); family rotation is the secondary safeguard.

**Oversampling**: trace-derived tasks (sourced from real zero-reward traces at 100% probe trigger rates) are repeated 3× before deduplication. These are the highest-fidelity pairs — grounded in actual production failure evidence rather than combinatorial templates.

**Target**: 600–1,200 valid pairs across train + dev splits after evaluator filtering.

**Output format**: TRL `SimPOTrainer` chat-message format — `{"prompt": [...], "chosen": [...], "rejected": [...], "_meta": {...}}` — written to `training_data/train.jsonl` and `training_data/dev.jsonl`. Build log in `training_data/build_log.json`.

**Contamination guard**: `generation_scripts/contamination_check.py` is rerun against the held-out partition after pair generation, before any training begins. No pair is derived from a held-out task.

**Contamination check result (2026-04-30 rerun)**: The check reports `status: FAIL` with 2 n-gram violations, both between held_out task `tb-prog-bjl-069` and train tasks `tb-prog-bjl-065/067`. These are template-generation artifacts: all three tasks are programmatic P015/bench-jargon variants that share the `prior_thread` boilerplate `"Do you have engineers who could start soon?"` and the `America/New_York` timezone in their input fields. The shared n-grams are prospect-supplied input text, not labels or answer keys. The specific forbidden phrase differs across the three tasks (`"bench"`, `"on the bench"`, `"bench strength"` respectively), so no label information is shared. The embedding similarity check (cosine < 0.85) and content hash check both passed with 0 violations. This known limitation of programmatic template generation does not constitute answer-key leakage; no training pairs were removed as a result. See `contamination_check.json` for the full violation record.

## Key Paper References

1. Rafailov et al., "Direct Preference Optimization," NeurIPS 2023. `arXiv:2305.18290` — reference model mechanism and log-ratio formulation; informed the decision to replace DPO's distributional bound with an external evaluator monitor.
2. Meng, Xia, and Chen, "SimPO: Simple Preference Optimization with a Reference-Free Reward," NeurIPS 2024. `arXiv:2405.14734` — algorithm of record; γ hyperparameter and memory efficiency justification.
3. Kim et al., "Prometheus 2," EMNLP 2024. `arXiv:2405.01535` — rubric-grounded training data design; adopted the principle of anchoring every pair to a named check type from the scoring evaluator.
4. Li et al., "Preference Leakage," 2025. `arXiv:2502.01534` — family rotation as secondary leakage prevention; evaluator-pass validation as the primary control that the paper's setup lacks.
